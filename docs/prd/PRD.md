## 2. 执行摘要

本 PRD 定义了数学 AI 助手的**问答后自动跟进推荐**功能：当用户提出一道数学解题类问题并获得 AI 解答后，系统自动分析该题的知识点与题型，智能推荐 **2 道难度递增**的相关练习题（基础巩固 → 能力提升），帮助用户逐步深化理解。

**核心价值主张**：将"被动问答"升级为"主动学习闭环"，用户每解决一个问题后立即获得针对性练习，形成 `提问 → 解答 → 练习 → 巩固` 的学习闭环。

## 3. 问题陈述

### 3.1 当前痛点

| 痛点 | 描述 | 影响 |
|------|------|------|
| **学习链路断裂** | 用户获得解答后没有后续练习环节，知识点停留在一知半解 | 学习效果差，遗忘率高 |
| **手动推荐繁琐** | 用户需主动请求推荐题目，增加操作成本 | 推荐功能使用率低 |
| **无难度梯度** | 现有推荐工具返回的题目难度单一或随机排列 | 无法满足循序渐进的学习需求 |

### 3.2 目标指标

- **触发准确率** ≥ 95%（数学解题类问题正确触发，非解题类问题不误触发）
- **推荐相关性** ≥ 80%（推荐的练习题与原题在知识点/题型上高度相关）
- **降级成功率** = 100%（任何异常情况下都有兜底输出，不出现空白/报错）
- **额外延迟** ≤ 3 秒（推荐过程对用户体验的影响控制在可接受范围）

## 5. 用户角色与场景

### 5.1 核心用户角色

**学生用户（主要）**：
- 正在学习高等数学（微积分/线性代数等）
- 通过 AI 助手解答不会的数学题
- 希望获得针对性的练习来巩固知识
- 对 LaTeX 公式渲染有基本认知

### 5.2 关键使用场景

**场景 A：正常推荐流程（Happy Path）**

```
Given: 用户输入 "已知函数 f(x) = x^3 - 3x^2 + 2x + 1，求 f(x) 在 x=1 处的导数值"
When: AI 完成解答并流式输出完毕
Then: 系统自动：
  1. 判定该问题为"数学解题类"（计算题/导数）
  2. LLM 提取：category=导数, knowledge_points=["导数定义","导数计算"], question_type=计算题
  3. DifficultyEstimator 计算两道题的难度：Q1=基础(2级), Q2=进阶(4级)
  4. RAG 引擎从题库检索出2道相关题
  5. 追加格式化文本到 AI 回复末尾，通过 SSE 发送
  6. 前端渲染出带难度标签的两道练习题
```

**场景 B：RAG 降级流程**

```
Given: 用户输入一道数学题，但 RAG 引擎不可用 / 无匹配题 / 超时
When: 推荐引擎调用失败（任意异常）
Then: 系统自动切换到 LLM 兜底模式：
  1. 捕获异常，记录日志
  2. 调用 LLM 根据提取的知识点和题型生成2道原创练习题
  3. 标注来源为 "AI 生成"
  4. 正常追加到回复末尾
```

**场景 C：非解题类问题（不触发）**

```
Given: 用户输入 "什么是导数的几何意义？"（概念解释类）
When: AI 完成解答
Then: 系统判定该问题不属于"数学解题类"，不触发推荐
      用户只看到纯文字回答，无练习题追加
```

## 6. 功能需求

### FR-001: 数学解题类意图检测

| 属性 | 内容 |
|------|------|
| **描述** | 在 agent 处理用户输入前/中，判断当前问题是否属于需要触发推荐的"数学解题类"问题 |
| **优先级** | Must |
| **理由** | 这是整个功能的门控条件，错误判断会导致误触发或不触发 |
| **验收标准** | AC1: 计算/证明/求解类问题（含公式/数值/求xxx）→ 触发<br>AC2: 概念解释/闲聊/问候类问题 → 不触发<br>AC3: 判断延迟 < 100ms（不影响整体体验）<br>AC4: 边界情况：含公式的概念问题（如"用定义证明导数公式"）→ 触发 |
| **可测试性** | 准备 20 条测试用例（10条应触发 + 10条不应触发），断言准确率 |

### FR-002: 原题知识点与题型提取

| 属性 | 内容 |
|------|------|
| **描述** | 使用 LLM 从用户原始输入文本中结构化提取 category、knowledge_points（数组）、question_type |
| **优先级** | Must |
| **理由** | 提取质量直接决定推荐的相关性 |
| **验收标准** | AC1: 返回 JSON 格式 `{category, knowledge_points[], question_type}`<br>AC2: knowledge_points 至少提取 1 个有效值<br>AC3: category 必须与题库中已有 category 匹配（否则回退到默认值）<br>AC4: 提取超时 ≤ 5s，超时则使用关键词兜底映射<br>AC5: 对 LaTeX 公式内容的提取准确性 ≥ 85% |
| **可测试性** | Mock LLM 返回，验证解析逻辑和默认值回退 |

### FR-003: 双题难度递增计算

| 属性 | 内容 |
|------|------|
| **描述** | 利用现有 DifficultyEstimator 为同一用户计算两个不同的难度等级，确保 Q1 < Q2 且形成合理梯度 |
| **优先级** | Must |
| **理由** | 难度递进是核心体验差异点 |
| **验收标准** | AC1: Q1 难度 ∈ [1, 3]（入门~标准），Q2 难度 ∈ [3, 5]（标准~挑战）<br>AC2: Q2 - Q1 ≥ 1（确保有梯度）<br>AC3: 新用户（无历史数据）默认 Q1=2, Q2=3<br>AC4: 高水平用户（正确率 > 80%）Q1≥3, Q2≥4<br>AC5: 复用现有 DifficultyEstimator 四因子算法，不重复实现 |
| **可测试性** | 不同用户画像下验证难度分配合理性 |

### FR-004: 相关性多维度匹配检索

| 属性 | 内容 |
|------|------|
| **描述** | 基于提取的知识点、分类、题型，从题库中检索最相关的 2 道题目 |
| **优先级** | Must |
| **理由** | 决定推荐质量的核心算法 |
| **验收标准** | AC1: knowledge_points 权重最高（≥50%），category 次之（≥30%），question_type 辅助（≤20%）<br>AC2: 两道题不能是同一道题（去重）<br>AC3: 排除用户近30天已练题目<br>AC4: 若某难度级别无足够候选题，放宽 ±1 难度范围重试<br>AC5: 检索耗时 ≤ 2s |
| **可测试性** | 构造测试数据集，人工标注相关性评分，对比算法排序 |

### FR-005: Agent 层集成与 SSE 追加

| 属性 | 内容 |
|------|------|
| **描述** | 在 `MathAgent.stream()` 方法完成 full_response 收集后，异步执行推荐逻辑并将结果追加到 SSE 输出中 |
| **优先级** | Must |
| **理由** | 这是连接推荐引擎和前端的桥梁 |
| **验收标准** | AC1: 推荐逻辑异步执行，不阻塞主回复的 SSE 流输出<br>AC2: 主回复完成后，追加一个独立的 SSE 事件（type=follow_up 或嵌入 content）<br>AC3: 推荐内容格式：标题 + 2道题（各含 ID/来源/难度/内容）+ 分隔线<br>AC4: 推荐失败时主回复不受影响（隔离原则）<br>AC5: 追加内容兼容现有前端 Markdown+KaTeX 渲染管线 |
| **可测试性** | 端到端测试：发送解题类问题 → 验证 SSE 输出中包含推荐内容 |

### FR-006: LLM 兜底生成

| 属性 | 内容 |
|------|------|
| **描述** | 当 RAG 引擎调用失败时，自动切换到 LLM 根据知识点和题型生成 2 道原创练习题 |
| **优先级** | Must |
| **理由** | 保证 100% 降级成功率，永不出现空白输出 |
| **验收标准** | AC1: 触发条件：数据库不可用 / 无匹配题目 / RAG 超时(>3s) / 任何未捕获异常<br>AC2: LLM 生成的题目必须包含：完整题目内容 + 参考答案 + 来源标记"AI生成"<br>AC3: 生成的两道题同样遵循难度递增规则<br>AC4: 兜底切换时间 < 500ms（用户几乎无感知）<br>AC5: 所有降级事件记录到日志（含原因） |
| **可测试性** | Mock RAG 引擎抛异常，验证降级流程和输出格式 |

### FR-007: 前端渲染适配

| 属性 | 内容 |
|------|------|
| **描述** | 推荐内容通过现有 MessageItem.vue 的 Markdown+KaTeX 渲染管线正确展示 |
| **优先级** | Should |
| **理由** | 第一版复用现有渲染，最小化前端改动 |
| **验收标准** | AC1: 推荐区域有视觉分隔（如 `---` 分隔线 + 小标题）<br>AC2: 每道题显示：序号、ID、来源、难度等级、题目内容<br>AC3: LaTeX 公式正确渲染（KaTeX）<br>AC4: 不影响上方 AI 回复的正常展示<br>AC5: 推荐区域样式可通过 CSS 类名 `follow-up-practice` 定制 |
| **可测试性** | 浏览器截图对比，验证渲染效果 |

### 7.1 性能

| 指标 | 要求 |
|------|------|
| **端到端额外延迟** | ≤ 3 秒（从主回复结束到推荐内容显示） |

| 指标 | 要求 |

### 7.4 安全性与约束

| 指标 | 要求 |

## 11. 安全与风险

### 11.1 风险矩阵

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| LLM 提取超时导致体验卡顿 | 中 | 高 | 设置 5s 超时 + 关键词兜底映射 |
| RAG 检索无匹配题目 | 中 | 低 | LLM 兜底生成（已设计） |
| 意图检测误判（不该触发的触发了） | 低 | 中 | 规则+LLM 双重校验，保守策略 |
| 推荐内容打断 AI 回复展示 | 低 | 高 | SSE 异步追加，独立事件 |
| LLM 生成题目质量不稳定 | 中 | 中 | 结构化 prompt + 少样本示例 |

### 11.2 安全要求

- LLM 提取 prompt 不得包含原始用户输入的直接拼接（防注入）
- 推荐服务仅 READ 权限访问 questions 表
- 所有降级事件记录日志但不暴露给终端用户

### E1-1: 双难度计算

**目标**：为同一个用户计算两个递增的难度等级

**验收标准**：
- [ ] 复用现有 `DifficultyEstimator.estimate()` 方法
- [ ] Q1 难度 = `estimate(category, context="practice") - delta`（delta≥0，确保不低于1）
- [ ] Q2 难度 = `estimate(category, context="challenge")`（更高难度）
- [ ] 确保 `difficulty_q2 > difficulty_q1`
- [ ] 新用户默认 Q1=2, Q2=3

**验证命令**：不同 user_id 场景下的难度输出检查

### E1-2: 相关性检索

**目标**：基于多维度评分从题库检索 2 道最相关的题目

**验证命令**：构造特定知识点的查询，验证返回题目的相关性

### E1-3: LLM 兜底生成
