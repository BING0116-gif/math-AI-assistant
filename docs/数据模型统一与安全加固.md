## 2. 执行摘要

本阶段解决项目当前最严重的三个系统性风险：

1. **数据层碎片化** — 认证用户存储在内存字典中，错题本存储在 JSON 文件中，记忆数据分散在多个表与文件中，缺乏统一的数据治理。这导致数据不一致、难以备份、无法扩展。
2. **数据库迁移不可靠** — 混合使用 `Base.metadata.create_all` + 原始 SQL 迁移脚本（`003_add_user_skills.sql`, `004_add_migration_status.sql`, `005_create_memory_tables.sql`），无法回滚、无法版本控制、生产环境风险高。
3. **安全漏洞** — 缓存使用 `pickle` 反序列化（RCE 风险）、聊天端点 `/api/chat/*` 在免认证列表中、错题本无用户隔离、缺少 CORS 策略和输入验证。

方案通过 8 个 Epic 分步实施，覆盖数据模型统一、Alembic 迁移替换、安全加固三大目标，并全量修复遗留的 50 个测试失败。

## 3. 问题陈述

### 3.1 数据层碎片化

| 数据类型 | 当前存储方式                              | 问题                     |
| ---- | ----------------------------------- | ---------------------- |
| 认证用户 | 内存字典 `_users_db`                    | 进程重启后丢失，无法多进程共享        |
| 用户资料 | SQLAlchemy `users` 表                | 与内存字典不互通，存在两份用户数据      |
| 错题本  | JSON 文件 `error_book.json`           | 无用户隔离，并发写入竞态，无法 SQL 查询 |
| 记忆数据 | `learning_records` 表                | 模型正确，但与其他数据源缺乏统一视图     |
| 聊天会话 | `chat_sessions` + `chat_messages` 表 | 数据完整，但存在部分重复查询逻辑       |

**影响**：新增功能时需处理多个数据源，维护成本高；数据一致性无法保证；用户隔离不完整，可能导致数据泄露。

### 3.2 数据库迁移不可靠

当前 `init_db()` 函数执行以下流程：

1. `Base.metadata.create_all` — 创建所有表（幂等，但无法迁移）
2. 顺序执行 `003_add_user_skills.sql`, `004_add_migration_status.sql`, `005_create_memory_tables.sql`
3. 使用 `sqlite3` 连接直接执行 SQL（绕过 SQLAlchemy 引擎）

**问题**：

* 无法回滚失败的迁移

* 无法版本控制 — 重复执行可能报错

* `PRAGMA foreign_keys=OFF` 禁用外键约束

* 迁移脚本硬编码数据库路径

### 3.3 安全漏洞

| 漏洞              | 位置                                     | 严重程度   | 说明                                  |
| --------------- | -------------------------------------- | ------ | ----------------------------------- |
| Pickle 反序列化 RCE | `app/services/cache.py:45`             | **严重** | `pickle.loads(cached)` 可执行任意代码      |
| 聊天端点未认证         | `middleware_config.py` NO\_AUTH\_PATHS | **高**  | `/api/chat` 等端点公开访问                 |
| 错题本无用户隔离        | `error_book.py`                        | **高**  | 所有用户共享一个 JSON 文件                    |
| 缺少 CORS 策略      | 暂无 CORS 中间件                            | **中**  | 无法限制跨域访问                            |
| 缺少输入验证          | 多个 API 端点                              | **中**  | 无请求体大小限制和类型校验                       |
| 外键约束关闭          | `database.py:71`                       | **低**  | `PRAGMA foreign_keys=OFF` 导致数据完整性风险 |

## 5. 角色与场景

### 5.1 角色

| 角色         | 描述                           | 数量 |
| ---------- | ---------------------------- | -- |
| **学生**     | 使用数学 AI 助手做题、查错题、查看学习报告的终端用户 | 多数 |
| **开发者（你）** | 维护和开发系统的唯一开发者                | 1  |

### 5.2 关键场景

**场景 A：学生登录后使用聊天功能**

* Given 学生已登录并获得 JWT Token

* When 学生发送聊天请求到 `/api/chat`

* Then 系统应验证 JWT Token，返回 401 若未认证，返回 200 若认证通过

**场景 B：学生查看错题本**

* Given 学生 A 和学生 B 各有错题记录

* When 学生 A 查看错题本

* Then 只应看到学生 A 的错题，不包含学生 B 的数据

**场景 C：开发者执行数据库迁移**

* Given 开发者修改了数据模型

* When 执行 `alembic upgrade head`

* Then 数据库应自动迁移到最新版本，无需手动执行 SQL 脚本

**场景 D：系统使用 Redis 缓存**

* Given 缓存中有序列化数据

* When 系统读取缓存数据

* Then 应使用 JSON 反序列化，不执行 pickle 反序列化

## 8. 技术栈决策

### 8.1 已批准的技术栈

| 层          | 技术                               | 版本   | 说明                              |
| ---------- | -------------------------------- | ---- | ------------------------------- |
| **语言**     | Python                           | 3.12 | 不更改                             |
| **Web 框架** | FastAPI                          | 当前   | 不更改                             |
| **ORM**    | SQLAlchemy                       | 2.x  | 不更改，扩展模型                        |
| **数据库迁移**  | Alembic                          | 最新   | **新增**，替换 `create_all` + 原始 SQL |
| **数据库**    | SQLite (开发) / PostgreSQL 15 (生产) | 当前   | 不更改                             |
| **缓存**     | Redis 7 + 本地 JSON 序列化            | 当前   | 仅更改序列化方式                        |
| **向量库**    | Qdrant                           | 当前   | 仅修复测试                           |
| **测试框架**   | pytest + pytest-asyncio          | 当前   | 不更改                             |
| **CI/CD**  | GitHub Actions                   | 当前   | 不更改                             |

### 8.2 替代方案与拒绝原因

| 替代方案                       | 拒绝原因                                      |
| -------------------------- | ----------------------------------------- |
| 使用 `jsonpickle`            | 功能类似但仍有风险，不如直接使用标准 `json`                 |
| 使用 `msgpack`               | 新增依赖，收益有限，`json` 足够且更安全                   |
| 使用 `SQLite` 替代 `pickle` 缓存 | 复杂度高，Redis 缓存是正确的方案，仅需修复序列化               |
| 使用 `Flask-Migrate`         | 项目已使用 FastAPI，Alembic 是 SQLAlchemy 官方迁移工具 |

### 8.3 禁止替换

* 禁止替换 FastAPI 为其他 Web 框架

* 禁止替换 SQLAlchemy 为其他 ORM

* 禁止替换 Redis 为其他缓存系统

* 禁止替换 Qdrant 为其他向量库

## 11. 安全、风险与合规

### 11.1 数据分类

| 数据类型      | 分类   | 处理要求                      |
| --------- | ---- | ------------------------- |
| 用户密码哈希    | 敏感   | 使用 PBKDF2-SHA256 存储，日志中脱敏 |
| JWT Token | 敏感   | 不在日志中记录，不通过 URL 传递        |
| 答题记录      | 内部公开 | 按用户隔离存储                   |
| 错题内容      | 敏感   | 按用户隔离存储                   |
| API 密钥    | 机密   | 仅通过环境变量注入，不落盘             |

### 11.2 秘密处理

* 所有 API 密钥通过 `.env` 文件或环境变量注入

* 不在代码中硬编码任何密钥

* JWT 密钥在 `.env` 中配置，默认值仅用于开发

### 11.3 日志安全

* 日志中不记录密码字段、Token 值、API 密钥

* 用户 ID 可以记录（用于审计）

* 请求体内容超过 1000 字符时截断

### 11.4 威胁假设

| 威胁                 | 缓解措施              |
| ------------------ | ----------------- |
| 未授权用户访问聊天 API      | 强制 JWT 认证         |
| 用户 A 访问用户 B 的错题    | 所有查询按 user\_id 过滤 |
| 通过 pickle 反序列化执行代码 | 替换为 JSON 序列化      |
| XSS 攻击             | 添加 CSP 头和 XSS 保护头 |
| CSRF 攻击            | 添加 CORS 策略        |

### 11.5 审查要求

* 所有代码变更在合并前由开发者（你）审查

* 迁移脚本变更需验证 `downgrade` 路径

* 安全相关变更需运行完整测试套件
