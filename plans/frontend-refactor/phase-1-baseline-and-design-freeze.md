# Phase 1：可信基线与设计冻结

> 前置条件：现有工作树和当前知识目录开发状态可读取  
> 建议周期：3～5 个工作日  
> 下一阶段：[Phase 2：设计系统与应用外壳](./phase-2-design-system-and-app-shell.md)

## 1. 阶段目标

在任何大规模 UI 修改之前，建立可重复的运行、测试和行为基线，并冻结本轮重构的范围、信息架构、设计方向和接口依赖。

阶段结束时，团队应能回答：

- 当前哪些功能真的可用？
- 重构后哪些行为必须保持？
- 哪些视觉与交互规则是唯一标准？
- 哪些接口能够直接复用，哪些需要 Phase 3 补充？
- 如果重构出现回归，如何快速定位？

## 2. 用户故事

- 作为开发者，我可以在干净环境中启动前后端并验证核心页面。
- 作为测试者，我可以用固定账号和固定数据复现文字提问、课程浏览和错题操作。
- 作为产品负责人，我可以通过一份冻结清单确认本轮做什么、不做什么。
- 作为后续开发 Agent，我可以仅依靠仓库文档理解当前架构、运行命令和完成标准。

## 3. 范围

### 本阶段必须完成

- 记录并保护现有未提交改动，尤其是知识目录、知识点学习内容、迁移和相关测试；
- 固定 Python、Node、数据库、Qdrant、Redis 的开发版本或镜像版本；
- 跑通或明确记录后端测试、前端生产构建、Alembic 空库升级、Docker Compose 配置；
- 建立 5 条重构前冒烟路径；
- 输出现有页面和组件责任清单；
- 冻结导航、路由、设计令牌方向和本轮非目标；
- 建立前端错误、加载、空状态的统一行为约定；
- 记录当前基准截图或等价的视觉证据。

### 本阶段不做

- 不重写页面布局；
- 不改变后端业务逻辑；
- 不添加新课程或大批量题目；
- 不引入新的组件库或 CSS 框架；
- 不处理所有历史技术债，只登记阻塞本次重构的债务；
- 不以“顺手优化”为由改动 Agent、RAG、Prompt 或数据库结构。

## 4. 已知现状与风险

- 当前工作树包含大量用户未提交修改，不允许覆盖或清理；
- 当前可用 bundled Python 缺少 pytest，原项目 venv 状态曾不可用；
- 前端生产构建在当前沙箱中出现过配置读取权限错误，需要在真实开发环境复验；
- `ChatView.vue`、`Sidebar.vue` 等组件体积较大，行为基线必须先于拆分；
- 主题 SCSS 变量与 CSS 自定义属性存在主色和语义冲突；
- 对话主要存储在 Pinia/localStorage，后端已有 ChatSession/ChatMessage 模型，当前边界需如实记录；
- 知识目录与学习页面仍在开发，不能把半成品误标为稳定基线。

## 5. 纵向切片

### Slice 1.1：可复现启动与健康检查

#### 要做什么

为“注册/登录 → 首页 → 文字提问 → 查看知识目录”建立一套可重复启动流程。开发配置允许 SQLite，但生产/Compose 默认使用 PostgreSQL。

#### 涉及层

- 环境与依赖；
- Docker Compose；
- Alembic；
- FastAPI 健康检查；
- Vite 构建与代理；
- 基础认证。

#### 验收标准

- README 中的命令可以由新开发者执行；
- 空 PostgreSQL 可以升级到最新迁移；
- 前端可以访问后端健康检查；
- API Key 不存在时有明确错误，不导致无提示白屏；
- Compose 配置不隐式连接开发者本地 SQLite；
- 所有阻塞项记录实际命令、输出和解决方式。

### Slice 1.2：核心行为冒烟基线

#### 要做什么

建立五条用户可见行为的自动化或半自动化基线：

1. 注册/登录并保持身份；
2. 发送文字数学问题并接收 SSE；
3. 上传/粘贴图片题并获得识别或可恢复错误；
4. 浏览课程树并打开知识点学习页；
5. 将题目加入错题本、更新并删除。

#### 验收标准

- 每条路径都有固定输入、预期输出和数据清理策略；
- 用户 A 不能看到用户 B 的错题、画像或对话；
- 关键网络失败具有可见错误；
- 测试不依赖已有本地数据库；
- 基线失败与新增失败可以区分。

### Slice 1.3：前端责任与数据契约审计

#### 要做什么

梳理页面、组件、store、API 模块和存储边界，形成“保留/拆分/替换/删除候选”矩阵。

重点确认：

- `LayoutDefault`、`Sidebar`、`TopBar` 如何迁移到新 AppShell；
- `ChatView` 中流式通信、错题弹窗、推荐、滚动和输入分别归属哪里；
- `KnowledgeCatalogView` 与 `KnowledgeLearningView` 依赖的 API；
- `ErrorBookView` 与 store 的数据来源；
- 主题切换、登录状态和聊天历史的持久化边界；
- Markdown/KaTeX 是否存在多条渲染管线。

#### 验收标准

- 每个核心模块有唯一责任说明；
- 页面不直接承担的逻辑已列为 Phase 2/3 拆分候选；
- 当前 API 请求与响应字段有示例；
- 对不存在或不稳定的接口明确标记，不在 Phase 2 中假装可用；
- 标出刷新后可能丢失的数据。

### Slice 1.4：范围和设计冻结

#### 要做什么

确认本轮信息架构与设计规则，形成评审通过的冻结清单。

首批一级导航：

- 今日（`/`）；
- 提问（`/chat`）；
- 课程/知识（`/knowledge`）；
- 错题复盘（`/error-book`）。

学习路径、资料库和完整知识图谱在有真实功能前不得做成无反馈的空入口。

#### 验收标准

- 使用 `docs/UI_UX_MASTER_PLAN.md` 作为视觉方向源；
- 色彩、字体、间距、圆角、阴影、动效和断点有明确范围；
- 页面信息架构和路由映射获得确认；
- Phase 2 不涉及后端模型调整；
- 列出本轮明确不做的内容；
- 设计评审结论能够被后续开发直接引用。

## 6. 建议产物

- 环境与测试基线记录；
- 核心路径冒烟用例；
- 页面/组件/接口审计矩阵；
- 重构前关键页面截图；
- 设计与范围冻结记录；
- 已知失败和技术债清单；
- Phase 2 的可执行入口条件。

## 7. 测试策略

- 后端：pytest 收集、关键安全与知识目录测试；
- 数据库：空库 Alembic 升级和基础种子幂等；
- 前端：生产构建；若尚无测试框架，先以最小冒烟脚本记录行为；
- E2E：优先 Chromium，一条路径一个独立用户和数据上下文；
- 手工：375px、768px、1440px 截图及主要交互记录。

## 8. 推荐切片/PR 顺序

1. 环境与冷启动基线；
2. 冒烟路径与测试数据；
3. 组件/API 审计文档；
4. 设计和范围冻结。

## 9. 风险控制

- 不修复与重构无关的历史问题；
- 不删除现有页面或旧主题；
- 不修改用户未提交内容；
- 构建环境不通时必须保留静态编译、配置校验等可获得证据，但不能宣称全量通过；
- 设计讨论超过两天仍未收敛时，按 UI 总纲默认值执行。

## 10. Definition of Done / 退出条件

- [ ] 核心服务可在记录的环境中启动；
- [ ] 五条冒烟行为有可重复证据；
- [ ] 空库迁移和基本身份隔离已验证；
- [ ] 页面、组件、store、API 和存储责任清晰；
- [ ] 路由与信息架构冻结；
- [ ] 设计方向和语义令牌范围冻结；
- [ ] Phase 2 无需重新讨论技术栈或品牌风格即可开始；
- [ ] 所有未解决阻塞均有责任人、影响和下一步。
