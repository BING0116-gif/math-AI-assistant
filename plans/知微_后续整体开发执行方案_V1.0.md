# 知微智能数学学习系统后续整体开发执行方案 V1.0

> 来源：`docs/知微_智能数学学习系统产品方案_V1.0.md`、当前仓库实现审计、`plans/math-ai-assistant-development-roadmap.md`  
> 编制日期：2026-08-14  
> 使用方式：本文件用于交给 Trae Work 按步骤实施。一次只执行一个编号步骤，完成代码、测试、文档和验收后，才能进入下一步。  
> 当前产品边界：首个正式版本聚焦大学高等数学，先完成“函数、极限与连续”的学习闭环。高中数学只作为未来课程包，不在当前版本同时开发。

---

## 1. 最终目标

把当前“具备聊天、知识目录、错题、记忆、RAG 和画像基础设施的数学 AI 原型”，收敛为一个即使千问 API 暂时不可用，也能完成以下流程的学习产品：

```text
注册 / 登录
→ 选择高等数学知识点
→ 学习概念与例题
→ 开始自主练习
→ 提交答案
→ 确定性判题
→ 记录作答事实
→ 自动进入错题本
→ 更新知识点掌握状态
→ 安排复习或推荐下一题
→ 复测与变式验证
→ 更新学习画像和今日任务
```

AI 只负责提示、讲解、开放式错因分析、视觉识题和变式生成；题目标准答案、客观题判定、学习记录、掌握度和复习时间不得只由 LLM 决定。

---

## 2. 全局架构决策

以下决策适用于所有阶段，后续步骤不得自行改变。

### 2.1 产品与课程边界

- 第一门正式课程为“大学高等数学”。
- 第一批内容范围为函数、极限、连续；导数、积分等在核心闭环稳定后扩展。
- 第一版题型只承诺选择题、判断题、数值填空题和受限数学表达式填空题。
- 通用手写大题自动批改、教师端、班级、家长端、排行榜、社交和 3D 知识星球不进入当前 MVP。

### 2.2 数据事实来源

- PostgreSQL 是用户、课程、知识点、题目、练习、作答、错题、掌握度和复习计划的唯一事实来源。
- Qdrant 只保存可重建的题目、教材片段和记忆向量索引，不保存权威业务状态。
- Redis 只用于缓存、限流和短期任务状态，不作为永久学习数据源。
- 聊天上下文必须逐步迁移为 SQL 可恢复会话；进程内历史只能作为缓存。
- 所有派生状态必须能根据不可变作答记录重算。

### 2.3 用户与权限

- 所有学生数据必须使用认证中间件提供的真实 `user_id`。
- 路由不得接受客户端传入的任意用户 ID 后直接操作数据。
- 所有查询和修改必须验证资源归属。
- 不得使用默认用户、共享 session key 或匿名数据混入正式画像。
- 数据导出、删除和审计能力必须覆盖新增表。

### 2.4 数据库变更

- Schema 只通过 `app/data/alembic/versions/` 中的 Alembic 迁移修改。
- 禁止使用运行时原始 SQL 迁移、`create_all` 或修改 `data/math_ai.db` 代替迁移。
- 每次迁移必须考虑已有数据、空 PostgreSQL 升级、外键、回滚或恢复方案。
- 新增学生范围表时必须包含 `user_id`、必要索引和删除策略。

### 2.5 API 契约

- 新接口统一使用 `/api/...` 前缀；认证接口保留现有 `/auth/...` 兼容行为。
- 请求与响应必须使用明确的 Pydantic 模型，不返回不稳定的自由字典。
- 时间使用带时区 UTC 时间；前端负责本地化显示。
- 列表接口必须支持分页或明确限制。
- 事件写入必须带幂等键；重复提交返回原结果，不重复更新技能或创建错题。
- 现有客户端字段如需调整，应先兼容旧字段，再同步更新客户端和测试。

### 2.6 AI 与离线模式

- 新增统一 `AI_ENABLED` 开关；缺少或停用 API Key 时应用仍必须启动。
- `AI_ENABLED=false` 时关闭聊天生成、视觉识题、LLM 复杂度分类和 AI 推荐解释，但练习、判题、错题、复习、画像和规则推荐继续可用。
- 所有模型调用必须经过统一服务边界，记录模型、Prompt 版本、耗时、token、错误和降级结果。
- 不允许业务服务各自直接创建模型客户端。
- 首版生产执行器只保留 ReAct；Plan-and-Execute 作为实验代码隔离，未通过质量评测前不进入路由。

### 2.7 核心领域模型

后续实现围绕以下概念收敛：

- `Course / Chapter / KnowledgePoint`：版本化课程知识结构。
- `Question`：已审核的标准题目。
- `PracticeSession`：一次练习或考试会话。
- `Attempt`：一次不可变的作答事实。
- `GradingResult`：对一次作答的判定结果和判定依据。
- `ErrorItem`：由错误作答产生的复盘对象。
- `UserKnowledgeState`：用户在某个知识点上的可重算学习状态。
- `ReviewSchedule`：到期复习计划。
- `ProfileSnapshot`：面向页面和 AI Prompt 的派生画像快照。

现有 `LearningRecord`、`UserSkill`、`ExamPaper`、`ExamSubmission` 可以迁移或复用，但必须先明确与上述模型的映射，禁止再创建第四套含义相近的数据。

## 3. Trae Work 执行规则

每次向 Trae Work 提交任务时，只提交一个步骤，并附带以下固定要求：

1. 开始前阅读 `AGENTS.md`、本方案和该步骤涉及的现有代码。
2. 先输出影响图：前端 API → FastAPI 路由 → 服务 → 仓储/模型 → 迁移 → 测试。
3. 检查工作区未提交改动，不覆盖与任务无关的用户修改。
4. 先补或更新测试，再实现业务行为；无法先写测试时说明原因。
5. 不顺手重构不在步骤范围内的模块。
6. 完成后报告修改文件、API 契约、数据不变量、迁移命令、测试结果和残余风险。
7. 只有满足该步骤全部验收标准，才把步骤标记为完成。
8. 测试或构建没有执行成功时必须如实记录，不得声称通过。

每一步的统一完成定义：

- 行为可由用户或 API 独立演示。
- 正常、空状态、错误状态和权限失败均有处理。
- 学生数据按 `user_id` 隔离。
- 新增契约有自动化测试。
- 新增数据有迁移和删除/导出考虑。
- 前端改动通过 Vitest 和生产构建。
- 后端改动通过受影响 pytest；合并阶段执行全量 pytest。
- 文档与当前实现一致。

# Phase 0：建立可信、可离线运行的工程基线

目标：不依赖千问余额，系统也能启动、登录、浏览课程并运行确定性功能；同时消除阻碍后续开发的契约漂移。

## Step 0.1：冻结当前基线并建立功能状态清单

### 开发内容

- 建立唯一的当前功能状态文档，按“已贯通、部分实现、仅骨架、未实现、暂缓”标记模块。
- 记录现有 6 个后端失败测试、前端无测试文件、前端构建环境问题和 Compose 必填变量问题。
- 明确当前未提交前端改动的归属，不在本步骤修改这些业务文件。
- 统一 README 中正式入口、PostgreSQL/Redis/Qdrant 依赖、启动方式和验证命令。
- 将“大学高等数学首版”写入当前状态与开发说明，解释与旧产品方案中“高中数学”的差异。

### 验收标准

- 新开发者能从文档判断每个主要模块的真实状态。
- 文档不再把数据模型或单元测试存在等同于功能已完成。
- 所有已知失败有原因和后续归属。

## Step 0.2：实现无千问 API 的离线启动模式

### 开发内容

- 在设置中增加 `AI_ENABLED`，默认行为必须明确。
- 调整应用装配，空 API Key 时不构建需要远程模型的 Agent/分类器。
- 给 AI 服务提供“不可用”状态对象，而不是在导入阶段抛异常。
- 聊天、识图、AI 分析接口在离线模式返回稳定、可识别的服务不可用响应。
- 前端根据能力状态禁用 AI 输入和图片入口，并显示后续可恢复的说明。
- 关闭离线模式下的 LLM 复杂度分类和 AI 推荐解释。
- `/api/health/detailed` 增加 AI 能力状态，AI 停用不应使整个服务 unhealthy。

### 测试

- 无 API Key 的应用导入和启动测试。
- 离线模式下非 AI 接口仍可用的集成测试。
- AI 接口离线响应契约测试。
- 前端离线状态组件测试。

### 验收标准

- 删除测试环境中的 API Key 后，FastAPI 能完整启动。
- 用户仍可登录、打开课程、查看错题和画像空状态。
- 不发生任何外部模型网络调用。

## Step 0.3：修复认证契约和前端统一登录状态

### 开发内容

- 更新旧 API 集成测试，使其符合现有强制认证策略。
- 建立统一前端认证 store 或服务，负责 token、用户信息、过期和退出。
- 将知识目录页内部的登录弹窗逻辑抽离为全局认证入口。
- 路由守卫统一处理受保护页面；401 时清理失效凭证并引导登录。
- 所有 API 客户端复用同一个 Authorization 注入和错误处理逻辑。
- 保留旧 token 键的兼容读取或提供一次性迁移。

### 验收标准

- 注册、登录、刷新、退出、401 过期流程一致。
- 未登录用户不能读取其他用户错题、画像、练习和聊天数据。
- 原有 6 个认证契约失败测试修复。

## Step 0.4：统一前端工程入口和测试基线

### 开发内容

- 确认 `router/index.js` 与 `router/index.ts` 的唯一正式实现，删除或迁移冲突版本。
- 新增至少一组可运行的 Vitest 测试，覆盖路由、认证 API 和数学渲染基础行为。
- 修复构建配置，使 `npm run test` 和 `npm run build` 在标准环境可重复执行。
- 明确 `frontend/dist` 是否提交；若不提交则清理跟踪规则，若提交则禁止历史哈希文件无限累积。
- 不在此步骤重做 UI。

### 验收标准

- Vitest 不再因“无测试文件”失败。
- 前端生产构建通过。
- 只有一套正式路由实现。

## Step 0.5：收敛画像与数据库方言问题

### 开发内容

- 列出 `UserProfileAnalyzer`、`MemoryPersistenceFacade`、`ProfileService`、`SkillAggregator` 的职责和调用者。
- 指定 `LearningRecord/Attempt` 为事实，`UserSkill/UserKnowledgeState` 为可重算状态，画像为派生快照。
- 移除或修复 `ProfileService` 中 MySQL 术语与 `ON DUPLICATE KEY UPDATE`，统一使用 SQLAlchemy/PostgreSQL upsert 或仓储。
- API 页面画像与 Agent Prompt 画像复用同一应用服务，不再分别拼装。
- 保持现有响应兼容；必要时增加版本字段。

### 测试

- PostgreSQL 画像写入和读取测试。
- 跨用户隔离测试。
- 重复事件不会重复更新画像测试。
- Redis 不可用时降级测试。

### Phase 0 完成标准

- 后端全量测试没有未登记失败。
- 前端测试与构建可运行。
- 无千问 API Key 可启动。
- PostgreSQL 空库可以 Alembic 升级至 head。
- Docker Compose 配置在提供示例环境变量后有效。

# Phase 1：题库、练习与确定性判题闭环

目标：交付第一个真正可使用的核心路径，不依赖 LLM 完成“学一个知识点并做题”。

## Step 1.1：冻结高数首版知识体系和题目规范

### 开发内容

- 将函数、极限、连续拆成约 20–30 个稳定知识点。
- 为知识点定义 code、名称、层级、前置关系、关联关系、难度和重要度。
- 扩展题目字段：课程、版本、知识点关系、题型、难度、预计时间、答案规范、解析步骤、常见错误、审核状态、来源和 AI 生成标记。
- 多对多知识点关系使用规范化关联表，不继续仅靠逗号字符串。
- 建立 `draft/reviewed/published/retired` 题目状态。
- 创建迁移和兼容旧题目的数据迁移策略。

### 内容要求

- 首批至少 100 道人工确认题。
- 每个知识点至少包含基础、标准两档题目。
- 正式题必须有答案、解析、来源、审核状态和至少一个知识点。

### 验收标准

- 课程树和题目均使用稳定 ID。
- 未审核题目不会进入正式练习。
- 旧题目不会因迁移静默丢失。

## Step 1.2：建立练习会话与不可变作答模型

### 开发内容

- 设计并迁移 `PracticeSession` 与 `Attempt`；明确是否复用 `ExamPaper/ExamSubmission` 和 `LearningRecord`。
- `PracticeSession` 至少记录用户、模式、知识范围、题目列表、状态、开始/结束时间和配置快照。
- `Attempt` 至少记录用户、会话、题目、答案、提交序号、耗时、提示使用、解析查看、AI 帮助、幂等键和提交时间。
- 作答事实原则上不可覆盖；再次提交创建新 attempt，并标记当前有效尝试。
- 明确 Attempt 如何生成或关联 LearningRecord，避免双写不一致。
- 更新用户数据导出和删除流程。

### 不变量

- Attempt 的 `user_id` 必须与 PracticeSession 的 owner 一致。
- 客户端不能替用户指定判题结果、正确答案或掌握度。
- 同一幂等键重复请求只产生一次事实记录。

## Step 1.3：实现自主练习创建与取题 API

### 开发内容

- 提供可用知识点、难度、题型和题量选项。
- 新增创建练习会话接口，由服务端筛选已发布题目。
- 取题时不得返回标准答案和完整解析。
- 题目不足时返回明确的可用数量和降级建议。
- 新增查询当前会话、题目导航和恢复未完成会话接口。
- 所有接口按认证用户隔离。

### 推荐路由

```text
GET  /api/practice/options
POST /api/practice/sessions
GET  /api/practice/sessions/{session_id}
GET  /api/practice/sessions/{session_id}/questions/{question_id}
```

### 验收标准

- 用户能按知识点和难度创建一次 5 题练习。
- 重复刷新不会改变会话题目集合。
- 无权用户访问会话返回 404 或 403，不泄露存在性和内容。

## Step 1.4：实现确定性判题引擎 V1

### 开发内容

- 选择题和判断题使用规范化值比较。
- 数值题支持整数、小数、分数、允许误差和必要单位规则。
- 受限表达式题实现安全解析、规范化和等价判断。
- 严禁对未清洗输入直接使用危险表达式执行或不受限 `parse_expr`。
- 判题结果包括 `correct/incorrect/needs_review/invalid`、判定方式、规范化答案和用户可见反馈。
- 对暂不支持的开放题返回 `needs_review`，不得伪装为确定判定。
- 每种题型建立正常、等价、格式错误、恶意输入和边界测试矩阵。

### 推荐路由

```text
POST /api/practice/sessions/{session_id}/attempts
```

### 验收标准

- `1/2` 与 `0.5` 可按规则判等。
- 支持的表达式等价案例有确定性测试。
- 无法可靠判断时明确进入待审核状态。

## Step 1.5：实现练习做题页面

### 开发内容

- 新增练习中心页面：自主练习为首个正式入口，AI 推荐和模拟考试显示为后续能力或受控入口。
- 新增做题页面：题干、选项/输入、题目导航、进度、提交、即时反馈和下一题。
- 练习模式允许提交后查看提示、解析和相关知识点。
- 保存并恢复未完成会话。
- 覆盖桌面和移动布局、键盘操作、加载、空状态和错误状态。
- 数学内容统一使用现有安全渲染组件。

### 验收标准

- 用户能从知识点页或练习中心进入练习并完成 5 道题。
- 刷新页面后进度可恢复。
- 正确答案不会在提交前出现在网络响应或页面状态中。

## Step 1.6：提交完成、结果页与学习记录落库

### 开发内容

- 新增完成练习接口，计算正确数、耗时和知识点表现。
- 结果页展示总览、每题结果、用户答案、正确答案、解析和下一步行动。
- 每次有效 Attempt 写入统一学习事实；不得由前端另行调用画像接口补写。
- 练习完成事件触发后续错题与技能更新，但主提交成功不应被非关键派生任务阻断。
- 为失败的派生任务建立可重试状态或重算入口。

### 推荐路由

```text
POST /api/practice/sessions/{session_id}/complete
GET  /api/practice/sessions/{session_id}/result
```

### Phase 1 完成标准

- 新用户可以完成“登录→选知识点→做题→判题→查看结果”。
- 该流程完全不依赖 LLM。
- 每次作答有不可变事实和幂等保证。
- API、服务、仓储、权限、组件和主链 E2E 均有测试。

# Phase 2：错题、技能、复习与学习画像闭环

目标：把一次练习转化为长期学习状态，而不是做完即结束。

## Step 2.1：统一固定错因分类体系

### 开发内容

- 固定首版枚举：`KNOWLEDGE_GAP`、`CONCEPT_MISUNDERSTANDING`、`CONDITION_MISSING`、`CALCULATION_ERROR`、`METHOD_SELECTION`、`FORMULA_MISUSE`、`CARELESS`、`UNKNOWN`。
- 确定性规则先分类可确定错误；AI 只补充开放式原因和建议。
- 错因结果包含类别、原因、关键错误步骤、建议、置信度、来源和版本。
- 低置信度 AI 分类使用 `UNKNOWN` 或要求用户确认。
- 错因标签必须可统计，不允许每次生成自由类别。

## Step 2.2：错题自动入本和复盘状态机

### 开发内容

- 错误 Attempt 自动创建或更新 ErrorItem，并关联原题、Attempt、知识点和错因。
- 建立状态机：`new → understanding → consolidating → mastered`。
- 原题重做正确不能直接毕业；必须满足原题、变式和间隔复测条件。
- 保留用户笔记、原答案、正确答案和历史复习记录。
- 重复错题按用户和题目聚合，但保留每次错误事实。
- 手动添加错题继续兼容，但标记来源和较低结构化置信度。

### 验收标准

- 错误作答自动出现在错题页。
- 重复提交不生成重复错题。
- 不同用户的同一道题产生相互隔离的错题状态。

## Step 2.3：统一 UserKnowledgeState 和技能聚合

### 开发内容

- 评估 `UserSkill` 是否直接升级为用户×知识点状态；若不能满足则新增 `UserKnowledgeState` 并提供迁移映射。
- 状态至少包含掌握度、记忆强度、置信度、尝试数、正确数、错题数、错误类型统计、最近练习、最近复习、下次复习和变式表现。
- 掌握度更新采用可解释规则，输入包括正确性、难度、提示、解析查看、耗时、复测间隔和变式表现。
- 每次状态变化记录原因和版本，支持重新计算。
- SkillAggregator 只消费规范化 Attempt/LearningRecord，不再依赖不稳定自由标签。

### 验收标准

- 同一批作答重复重算得到一致结果。
- 单次答对不会直接变成稳定掌握。
- 间隔后答对和变式答对的权重高于立即重做。

## Step 2.4：实现间隔复习计划

### 开发内容

- 新增或规范化 ReviewSchedule，关联用户、知识点/错题、上次复习、下次复习、次数、阶段和算法版本。
- 首版使用规则间隔，例如 1、3、7、15 天，并根据答题表现调整。
- 练习完成、错题重做和复测后更新计划。
- 提供今日到期复习列表、完成复习和延后接口。
- 定时任务只负责发现或维护到期状态，不替代事实写入。

### 验收标准

- 错题后能够生成下一次复习时间。
- 到期复习完成后自动安排下一次。
- 重复事件不会产生多条冲突计划。

## Step 2.5：实现规则推荐和今日任务

### 开发内容

- 候选来源：到期复习、近期薄弱知识点、当前章节和适度挑战题。
- 首版比例参考 40% 薄弱点、30% 到期复习、20% 当前章节、10% 提升挑战；比例可配置但必须可解释。
- 先做规则排序，再用题库筛选；没有 Qdrant 和 LLM 时仍能推荐。
- 每个推荐包含推荐原因、目标知识点、预计时间和启动入口。
- 首页/看板展示最多一个主要任务和少量备选，避免信息过载。

### 验收标准

- 每个推荐能说明使用了哪些真实学习证据。
- 无学习数据的新用户得到基础诊断或入门练习，而不是 0% 画像。
- 题目不足时有明确降级。

## Step 2.6：统一学习画像与看板

### 开发内容

- 画像只展示由统一状态服务生成的优势、风险、错误模式、学习习惯和建议。
- 区分掌握度、记忆强度、错误模式和迁移能力，不混成单一分数。
- 冷启动状态展示“尚在了解你”，不展示大量 0%。
- 看板只回答：有没有进步、最弱在哪里、下一步做什么。
- Agent Prompt、推荐器和前端读取同一版本画像快照。
- Redis 缓存失效不影响正确性。

### Phase 2 完成标准

- 错误作答会自动进入错题本、更新知识状态并安排复习。
- 复测会改变错题状态和下一次复习时间。
- 首页、画像、推荐和 Agent 使用相同学习状态。
- SQL/Qdrant/Redis 失败边界和修复路径有测试与文档。

# Phase 3：组卷、考试和 AI 辅导增强

目标：在确定性闭环稳定后接通考试场景，并在千问充值后恢复可测量的 AI 增强能力。

## Step 3.1：实现自主组卷与考试模式

### 开发内容

- 复用 PracticeSession 或收敛现有 ExamPaper，不维护两套重叠会话逻辑。
- 支持知识范围、难度、题型、题量和考试时间配置。
- 服务端按约束选题并保存试卷配置快照和题目顺序。
- 考试过程中禁止答案、解析、提示和 AI 辅导。
- 支持计时、自动保存、提交确认和超时提交。
- 提交后统一判卷并生成考试报告。

### 验收标准

- 考试模式网络响应在提交前不包含答案或解析。
- 刷新后考试时间和作答可恢复。
- 同一试卷提交幂等。

## Step 3.2：实现考试结果分析

### 开发内容

- 报告展示总分、正确率、耗时、知识点表现、错误类型和每题结果。
- 生成确定性的下一步练习入口。
- 报告统计只基于已完成判题结果。
- AI 总结为可选增强，失败时仍返回完整结构化报告。
- 把考试错误纳入错题、技能和复习链路。

## Step 3.3：恢复并收敛 AI Tutor

### 开发内容

- 充值后启用文本聊天和多模态能力。
- 学生模式仅暴露“只给提示、分步讲解、检查我的思路”，不暴露 ReAct/Planned 技术策略。
- 统一注入课程、知识点、用户画像和检索证据。
- 关键数学结论尽可能使用确定性工具检查。
- 结构化记录知识点、意图、工具、模型、耗时和成本。
- 聊天历史写入 SQL，并可在服务重启后恢复。

### 验收标准

- AI 不可用时不影响练习系统。
- 同一用户会话可恢复，不同用户无法读取。
- 回答能明确表达不确定性，不把模型输出当标准答案。

## Step 3.4：建立模型质量评测集

### 开发内容

- 建立文本题、图片题、模糊题、恶意输入、错误但貌似合理答案的评测矩阵。
- 每个案例保存期望答案、关键步骤、允许表达、知识点、允许工具和副作用。
- 评分维度：识别保真、最终正确、可验证推理、检索依据、工具调用、中文/LaTeX、安全和无跨用户泄漏。
- 模型和 Prompt 变更必须输出前后对比。
- 稳定确定性断言进入 pytest，开放式质量由人工金标复核。

## Step 3.5：评估并处理 Plan-and-Execute

### 开发内容

- 默认生产仍只使用 ReAct。
- 选取真正需要多工具、多阶段证明或长任务的评测样本。
- 在相同模型、预算和上下文下比较 ReAct 与 PlannedStrategy 的正确率、延迟、成本和失败恢复。
- 若 PlannedStrategy 没有显著收益，删除生产分类路由和闲置策略代码，保留决策记录。
- 若有显著收益，只对明确复杂任务启用，并增加超时、最大步骤和重规划限制。
- 复杂度分类器不得仅为修改 token 上限额外消耗一次 LLM 调用。

## Step 3.6：AI 智能组卷 V1

### 开发内容

- “智能”只负责根据技能状态生成结构化组卷蓝图，实际题目从已审核题库选择。
- 蓝图包含薄弱点、到期复习、当前章节和挑战题配额。
- 每道题提供基于真实记录的推荐原因。
- 不允许 LLM 临时生成整张正式试卷。
- 题目不足或蓝图冲突时回退为规则组卷。

### Phase 3 完成标准

- 自主组卷、考试、报告和错题链路贯通。
- AI 开关不影响确定性核心功能。
- 模型质量、成本和延迟有版本化报告。
- ReAct/Plan 是否保留由评测证据决定。

# Phase 4：变式训练、OCR、大题批改与产品化

目标：只在核心闭环和评测体系稳定后开发高风险高级能力，并完成真实学生试用。

## Step 4.1：变式训练 V1

### 开发内容

- 首版只支持少量可程序验证题型。
- 变式生成后执行答案计算、条件检查、数学等价验证和重复度检查。
- AI 生成题默认为 draft，不直接进入正式题库。
- 记录来源题、变化维度、生成模型、Prompt 版本和审核状态。
- 变式答题结果单独计入迁移能力。

### 验收标准

- 无法验证唯一答案的变式不会推给学生。
- 生成有效率、重复率和错误率可统计。

## Step 4.2：OCR 识别确认流程

### 开发内容

- 上传图片后先输出可编辑的结构化识别结果。
- 学生必须能确认或修正题干/答案，再进入讲解或批改。
- 保存原图引用、识别文本、修正文本、置信度和模型版本。
- 低置信度行明确标记。
- 图片存储、访问和删除遵循用户权限与保留策略。

## Step 4.3：受限大题 Rubric 参考评分

### 开发内容

- 只选择 1–2 种高数题型试点。
- Rubric 由人工预定义评分点，AI 只做证据匹配和解释。
- 输出必须称为“AI 参考评分”，并提供 OCR 与评分置信度。
- 学生可查看识别文本并提交争议反馈。
- 低置信度或超出支持题型时不自动给确定分数。

## Step 4.4：内容审核和题库运营

### 开发内容

- 建立题目导入、审核、发布、退役、问题反馈和修订流程。
- 正式内容记录来源、许可、审核者、版本和变更原因。
- 增加重复题、缺答案、缺知识点和异常难度审计。
- 不直接抓取或发布无授权商业题库内容。

## Step 4.5：可观测性、成本和数据恢复

### 开发内容

- 为请求、用户、会话、模型、工具、题目和学习事件建立结构化日志关联 ID。
- 统计接口错误率、判题待审核率、AI 调用成本、延迟、推荐点击和复测通过率。
- 建立 PostgreSQL 备份、Qdrant 重建、Redis 丢失恢复和事件重放说明。
- 增加 SQL/Qdrant 对账和修复命令，修复前先审计。
- 敏感数据不得进入模型日志或测试夹具。

## Step 4.6：真实学生试用与决策

### 开发内容

- 招募 10–30 名大学生进行两周试用。
- 观察注册完成率、首次练习完成率、7 日复习率、薄弱点复测通过率和严重错误率。
- 收集 AI 判错、OCR 修正、解析帮助和推荐有用性反馈。
- 输出“继续、调整、删除、延后”的功能决策清单。
- 试用前不扩展线性代数、概率论、教师端和商业化。

### Phase 4 完成标准

- 高风险 AI 功能有适用边界、置信度和人工纠错入口。
- 核心数据可备份和恢复。
- 真实试用证明至少一个可持续学习闭环具有价值。

## 5. 每阶段必须执行的验证

venv\Scripts\python.exe -m pytest <受影响测试> -q
venv\Scripts\python.exe -m pytest tests -q
```

数据库或迁移变更还必须：

cd frontend
npm.cmd run test
npm.cmd run build

docker compose config
```

不得将 `.env`、真实密钥、真实学生数据、`data/math_ai.db` 或 `qdrant_storage/` 提交为测试结果。

## 6. 北极星指标与阶段指标

### 北极星指标

> 每周从“不会/易错”变成“间隔复测后稳定掌握”的知识点数量。

### Phase 1 指标

- 练习创建成功率。
- 练习完成率。
- 判题 `needs_review` 比例。
- 作答幂等冲突率。
- 从知识点学习页进入练习的转化率。

### Phase 2 指标

- 错题自动入本成功率。
- 到期复习完成率。
- 错题原题重做通过率。
- 间隔复测通过率。
- 推荐任务启动率和完成率。

### Phase 3–4 指标

- 数学答案严重错误率。
- OCR 确认修改率。
- AI 判题争议率。
- 变式题有效率和重复率。
- 每次模型调用的成本、首字延迟和总延迟。

## 7. 暂缓和禁止事项

在 Phase 2 完成前禁止：

- 扩展到多门课程。
- 开发教师端、家长端、班级系统和商业化订阅。
- 新增另一套 Agent 框架、记忆框架或画像表。
- 开发复杂 3D 知识星球。
- 用 LLM 直接决定客观题正确性或正式掌握度。
- 让 AI 生成题未经验证直接进入正式练习。
- 以 Dashboard 数量、聊天次数或 Agent 数量作为完成度。
- 为一次性脚本引入新的生产运行时依赖。

任何新增功能必须回答：

1. 它进入哪一段学习闭环？
2. 它产生什么可靠学习数据？
3. 它如何改变下一步学习行动？
4. 没有 AI API 时是否仍有合理降级？
5. 它是否引入了新的事实来源或重复状态？

若无法回答，不应进入当前开发计划。
