# 智能数学助手完整开发方案

> 版本：v1.0（2026-08-04）  
> 依据：当前仓库代码、`docs/PRD.md`、`docs/STATUS.md`、`docs/UI_UX_MASTER_PLAN.md`、`docs/plans/calculus-knowledge-graph.md` 及现有测试目录  
> 目标：为项目确定未来 3～6 个月的产品与技术主线，不展开到函数级实现

## 1. 一句话方向

不要继续把项目做成“功能很多的数学聊天机器人”，而要收敛成一个能够完成以下闭环的大学数学学习系统：

> 诊断学生当前水平 → 讲清一个知识点 → 引导完成练习 → 验证答案与错因 → 更新掌握度 → 安排下一步与复习

首个可交付版本只聚焦 **高等数学中的函数、极限与连续**。先证明一个课程片段的闭环有效，再扩展微积分、线性代数、概率论等课程。

## 2. 当前项目处于什么阶段

### 2.1 已有基础

当前仓库已经具备一个中等规模 AI 学习产品的主要技术骨架：

- FastAPI 后端，具有聊天、识图、多模态、认证、错题本、画像、记忆、推荐、知识目录等 API；
- Vue 3 + Vite + Pinia + Element Plus 前端，已有首页、聊天、错题本、课程目录和知识点学习页；
- PostgreSQL/SQLite、SQLAlchemy、Alembic 数据层；
- Qdrant 向量检索、题库导入和 RAG 推荐；
- Qwen 文本与视觉模型接入、流式输出、Agent 与工具系统；
- `UserSkill`、学习记录、错题、用户画像与长期记忆等个性化数据；
- pytest 测试体系、安全隔离测试与 Docker Compose 部署骨架；
- 正在开发的高等数学知识目录、知识点学习内容和资源模块。

因此，项目已经过了“做出聊天功能”的阶段，约处于 **技术原型后期、产品 MVP 前期**。

### 2.2 当前最重要的问题

1. **能力多但主流程不够清晰**：聊天、知识图谱、推荐、错题本和记忆之间还没有形成学生可以持续使用的学习路径。
2. **完成状态不够可信**：代码、旧文档和真实运行状态存在偏差；当前 Python 环境缺少 pytest，前端构建也受到本机沙箱/工具环境影响，尚没有一条可重复的全量验证结果。
3. **课程内容仍偏薄**：技术系统大于课程内容，缺少经过审核的知识点、例题、练习、错因和评价标准。
4. **AI 回答质量缺少量化门槛**：目前更关注“能否生成”，还缺少针对数学正确性、步骤完整性、教学有效性和幻觉的评测集。
5. **前端仍偏功能集合**：缺少“今天做什么—学完发生什么—下一步去哪”的明确引导。
6. **题目系统仍默认 Mock**：远程出题适配器存在待实现项，正式题源、题目版权和数据质量策略尚未收口。

### 2.3 当前不应优先做的事

- 不要立刻扩展到所有大学数学课程；
- 不要先做复杂的 3D 知识星系、AI 自动建图或完整图谱管理后台；
- 不要继续新增多个 Agent 框架或频繁更换模型；
- 不要在没有评测集前用“模型看起来更聪明”作为优化依据；
- 不要让 LLM 直接决定标准答案、掌握度或正式课程内容；
- 不要同时重写前端、后端和数据层。

## 3. 产品定位

### 3.1 核心用户

- 正在学习高等数学、线性代数或概率统计的大学生；
- 基础不牢、跟不上课堂，希望获得分层讲解的学生；
- 考前需要诊断薄弱点、定向练习和错题复盘的学生。

首版不以教师管理、学校教务或大规模课堂管理为主要目标。

### 3.2 核心价值

- **讲得懂**：根据学生水平调整解释，而不是只输出标准答案；
- **算得对**：重要计算可由符号工具和规则验证，降低数学幻觉；
- **练得准**：练习来自当前知识点、错误类型和掌握度，而不是随机推荐；
- **记得住**：系统能记住学生的薄弱点，并按间隔复习安排再次检索；
- **看得见进步**：知识地图展示已掌握、学习中、薄弱和待解锁内容。

### 3.3 北极星指标

首版不要用“聊天次数”作为核心指标，建议使用：

> 每周完成至少一个“学习—练习—复测”闭环的活跃学生比例。

辅助指标：

- 首次提问后完成一道推荐练习的比例；
- 推荐练习完成率和正确率变化；
- 7 日复习回访率；
- 薄弱知识点复测通过率；
- 数学回答严重错误率；
- 首屏响应时间、完整回答耗时和单次回答成本。

## 4. 功能规划

### 4.1 P0：必须形成的学习闭环

#### A. 智能导师对话

- 支持文本、公式和题目图片输入；
- 自动识别课程、章节、知识点、题型和用户意图；
- 回答采用稳定结构：结论、思路、分步推导、结果检查、易错点、下一步；
- 提供“给提示而非答案”“换一种讲法”“生成变式”“我没懂这一步”等教学动作；
- 将本轮识别的知识点、题目和结果写入学习记录。

实现方式：保留现有流式聊天和 Agent 架构，在服务层增加统一的 `LearningContext` 概念，使聊天、推荐、错题和掌握度共享同一组课程与知识点 ID。

#### B. 高等数学课程学习空间

- 课程 → 章节 → 知识点目录；
- 每个知识点包含前置要求、概念直觉、定义/定理、推导、例题、练习和退出测验；
- 首版完成“函数、极限、连续”约 20～30 个核心知识点；
- 学生可从目录或聊天回答直接进入对应知识点。

实现方式：继续完成当前 `Course / Chapter / KnowledgePoint / KnowledgePointResource` 路径。PostgreSQL 是课程结构的唯一权威来源，Qdrant 只负责教材片段和题目的语义检索。

#### C. 练习与判题

- 每个知识点提供基础、标准、综合三级练习；
- 支持最终答案和关键步骤提交；
- 客观表达式优先由 SymPy 进行等价性验证；
- 主观证明或复杂推导由“规则检查 + LLM 评分量表”联合判断；
- 判题后先提示错误位置，再允许查看完整解答；
- 练习结果写入学习记录和掌握度。

实现方式：在现有 Question、LearningRecord、ExamPaper 模型上做纵向闭环，不另起一套题目数据。严禁直接对未清洗的用户表达式使用 SymPy `parse_expr`。

#### D. 错题复盘

- 聊天题和练习题都可进入错题本；
- 错题必须关联知识点、题型和错因；
- 错因至少区分：概念不清、条件遗漏、公式误用、计算错误、策略选择；
- 自动生成同知识点变式与同错因变式；
- 支持“已会”复测，复测通过后更新掌握状态。

#### E. 下一步推荐

- 每次学习或做题结束，只给 1 个主要下一步和最多 2 道练习；
- 推荐综合考虑前置关系、最近错误、掌握度、难度和复习到期时间；
- 推荐必须解释原因，例如“你在等价无穷小替换上连续出错”；
- 推荐失败不影响主回答。

实现方式：在现有 FollowUpRecommender、RAGRecommender、UserSkill 和 MathSkillDAG 基础上收口，先使用可解释规则排序，再用向量检索补充候选，不让 LLM 单独决定推荐。

### 4.2 P1：MVP 稳定后增加

- 今日学习工作台：待学习、待复习、继续上次任务；
- 2D 个性化知识地图：掌握、学习中、薄弱、可学习、锁定；
- 学习目标与轻量计划：按考试日期和每周可用时间生成；
- 资料库：上传课程讲义/PDF，回答显示引用来源；
- 阶段测验与学习报告；
- 线性代数首批内容；
- 管理员课程内容审核、题目审核与发布。

### 4.3 P2：验证留存后再做

- 概率论与数理统计课程；
- 教师班级与作业管理；
- 语音讲题、手写板和更强的公式 OCR；
- 3D 知识星系总览；
- AI 自动生成知识图谱草稿和批量题目标注；
- 多模型自动路由与成本优化平台；
- 校级多租户、付费订阅和运营后台。

## 5. 技术方案

### 5.1 保留的技术栈

| 层次 | 选择 | 用途与边界 |
|---|---|---|
| Web 前端 | Vue 3、Vite、Pinia、Vue Router、Element Plus | 保留现有栈，渐进重构，不重写 React |
| 数学渲染 | Markdown-it/Marked + KaTeX + DOMPurify | 统一为一条渲染管线，避免多套 Markdown 解析器行为不一致 |
| 后端 API | Python 3.11+、FastAPI、Pydantic | 异步 API、SSE、数据契约与权限校验 |
| 业务数据 | PostgreSQL、SQLAlchemy 2、Alembic | 用户、课程、题目、学习记录、错题、掌握度的权威数据 |
| 缓存/任务 | Redis | 仅用于缓存、限流、短任务状态；单机 MVP 可暂不引入复杂消息队列 |
| 向量检索 | Qdrant | 题目、教材片段和笔记的语义/混合检索，不保存权威业务关系 |
| AI | Qwen 文本模型 + Qwen-VL，保留模型适配层 | 文本讲解、意图识别、图片题目识别；业务层不绑定单一模型 SDK |
| 数学验证 | SymPy + 自定义规则 | 表达式等价、代数化简、求导积分校验；证明题不能只靠 SymPy |
| 部署 | Docker Compose + Nginx | 首版单区域部署；数据库、Qdrant、Redis 使用持久卷与备份 |

### 5.2 建议补充的工程栈

- 前端逐步迁移 TypeScript，新模块先用 TS，旧 Vue 文件不要求一次性重写；
- Vitest + Vue Test Utils 做前端单元和组件测试；
- Playwright 做注册、登录、提问、做题、加入错题、复测这条 E2E 主链；
- Ruff 或等价工具统一 Python lint/format；
- OpenTelemetry 或至少结构化日志记录 request、user、session、model、tokens、latency、cost、knowledge_point；
- CI 固定执行静态检查、后端测试、前端构建、E2E 冒烟和空 PostgreSQL 迁移；
- LLM 评测使用仓库内版本化数据集，不把人工抽查当作唯一质量门槛。

### 5.3 核心数据边界

必须统一以下稳定 ID：

- `user_id`：学生身份；
- `session_id`：一次对话；
- `course_id / knowledge_point_id`：课程知识体系；
- `question_id`：标准题目；
- `learning_record_id`：一次学习或作答行为；
- `error_item_id`：一次需要复盘的错误；
- `content_version / prompt_version / model_version`：内容与 AI 可追溯版本。

课程结构、题目标准答案和学习记录存 PostgreSQL；向量及可检索元数据存 Qdrant；图片/PDF 等原文件未来可放对象存储；Redis 不作为永久学习数据源。

### 5.4 AI 回答链路

推荐的稳定链路为：

1. 输入安全检查与身份确认；
2. 题目/OCR 结构化，识别课程、知识点和题型；
3. 从课程内容、题库和用户薄弱点检索上下文；
4. 按学生水平生成分层讲解；
5. 使用 SymPy、答案规则或第二检查流程验证关键结论；
6. 输出流式回答及引用；
7. 记录学习事件；
8. 更新掌握度并给出一个可执行的下一步。

LLM 输出尽量使用 Pydantic/JSON Schema 约束。面向用户的长文本可以流式输出，但课程标签、评分、错因和推荐候选必须结构化。

### 5.5 掌握度策略

首版不必上复杂知识追踪模型。采用可解释的规则分数即可：

- 正确性、题目难度、提示次数、作答时间、最近性和复测结果共同更新掌握度；
- 连续一次正确不能直接“已掌握”；
- 错题复测与间隔后的再次正确权重更高；
- 记录每次变化原因，允许以后替换为 BKT/IRT，而不改 UI 和业务事件。

## 6. 分阶段实施计划

以下周期按 1～3 人团队估算；单人开发应保留顺序并适当延长，不应同时展开所有阶段。

### Phase 0：建立可信基线（1～2 周）

#### 交付内容

- 固定可复现的 Python、Node 和 Docker 开发环境；
- 跑通全量 pytest、前端生产构建和空库 Alembic 迁移；
- 修复或登记已有失败，建立 CI 质量门禁；
- 整理 README 和状态文档，使其与当前 Vue/PostgreSQL/Qdrant 架构一致；
- 为注册登录、文字提问、图片提问、错题本、知识目录建立 5 条冒烟测试；
- 确认用户数据隔离和当前未提交的知识目录改动可以安全合并。

#### 验收标准

- 新环境按文档可在 30 分钟内启动；
- 后端测试、前端构建和数据库冷启动在 CI 中重复通过；
- 所有失败都有负责人或明确的已知基线；
- 不依赖本机残留数据库或手工修改才能演示。

### Phase 1：高数知识点学习闭环（2～3 周）

#### 交付内容

- 完成函数、极限与连续的课程目录和 20～30 个知识点；
- 每个知识点至少有概念说明、例题、基础练习和退出测验；
- 学生可从课程目录进入学习页，完成练习并看到即时反馈；
- 作答结果写入 LearningRecord 和 UserSkill；
- 学习页结束后能给出明确下一步。

#### 验收标准

- 一个新用户能够完成“注册 → 选知识点 → 学习 → 做题 → 看到掌握度变化”的完整流程；
- 内容、题目和知识点均使用稳定 ID；
- 至少 100 道题通过人工检查并完成知识点关联；
- 该路径有 API、组件和 E2E 测试。

### Phase 2：可信的数学导师（2～3 周）

#### 交付内容

- 统一文本、图片与多模态题目的分析链路；
- 回答支持提示模式、分层讲解、关键步骤检查和答案验证；
- 建立 100～200 道高数“金标评测集”；
- 对正确性、步骤完整性、知识点识别、引用正确性和教学表达打分；
- 失败时能够降级，例如说明无法验证，而不是伪造确定答案。

#### 验收标准

- 严重数学错误率达到项目预设门槛，且每次发布自动评测；
- 所有金标题保存标准答案、关键步骤、允许的等价表达和错误类型；
- 图片识别错误可由用户确认和修改题干；
- 模型或 Prompt 变更有版本和前后对比报告。

### Phase 3：个性化练习与复盘（2～3 周）

#### 交付内容

- 聊天结束、知识点学习结束后提供可解释的练习推荐；
- 错题按错因组织，支持同错因变式和定时复测；
- 今日页聚合待继续、待复习和推荐学习；
- 2D 知识地图展示掌握状态与解锁条件；
- 初版间隔复习与交错练习策略。

#### 验收标准

- 推荐结果始终满足课程前置关系和难度范围；
- 用户可以理解“为什么推荐这道题”；
- 错题复测会更新掌握度和下一次复习时间；
- 能统计从回答到练习、从练习到复测的转化漏斗。

### Phase 4：产品化与小规模试用（2 周）

#### 交付内容

- 统一今日、提问、知识地图、学习路径、错题复盘的信息架构；
- 完成移动端基础适配、加载/空状态/错误状态和可访问性；
- 增加限流、备份、告警、成本统计、隐私导出与删除；
- 邀请 10～30 名真实大学生完成 2 周试用；
- 收集任务完成率、学习效果、错误反馈和访谈记录。

#### 验收标准

- 核心 E2E 在生产构建上通过；
- 服务异常不会造成学习记录或错题静默丢失；
- 有每日成本、失败率和严重错误看板；
- 根据真实试用形成“继续、调整、删除”的功能决策清单。

### Phase 5：课程扩展与运营（持续）

扩展顺序建议：

1. 补全高等数学：导数、积分、级数、微分方程；
2. 线性代数：矩阵、线性方程组、向量空间、特征值；
3. 概率论与数理统计；
4. 再评估教师端、班级和商业化能力。

每增加一门课程，都必须同时增加知识体系、人工审核题库、评测集和学习效果指标，不能只改 Prompt。

## 7. 内容生产方案

课程内容是本项目后续最大的工作量，建议采用“AI 起草、人工审核、版本发布”流程：

1. 先由课程负责人确定课程大纲、知识点 ID 和前置关系；
2. AI 生成概念说明、例题和练习草稿；
3. 人工校验数学正确性、符号规范、难度和版权来源；
4. 通过审核后进入 published 版本；
5. 用户反馈与评测失败进入内容修订队列；
6. 所有正式内容保留来源、审核者和版本。

首版题目来源优先使用自编题、公开许可资源或已获得授权的材料。不要直接批量抓取教材和商业题库。

## 8. 质量保障

### 8.1 测试金字塔

- 单元测试：掌握度、推荐排序、DAG 校验、表达式判等、权限规则；
- API 集成测试：认证、课程、作答、错题、推荐、数据隔离；
- 前端组件测试：公式渲染、流式消息、学习步骤、判题反馈；
- E2E：完整用户闭环；
- LLM 离线评测：数学正确性、知识点识别、拒答与 Prompt 回归；
- 人工抽检：每次发布抽检高风险题型和图片题。

### 8.2 发布门槛

- 数据库迁移可升级且有回滚/备份方案；
- 核心测试全绿；
- 金标评测不低于上一稳定版本；
- 无 P0 安全问题和跨用户数据泄露；
- 新功能具有日志、指标、错误恢复和用户可见反馈；
- 课程内容已经审核，不以 AI 草稿直接上线。

## 9. 风险与控制

| 风险 | 控制方式 |
|---|---|
| AI 数学幻觉 | 工具验证、金标评测、答案不确定性提示、人工内容审核 |
| OCR 错题干 | 展示识别结果并要求用户可编辑确认 |
| 功能范围失控 | 只围绕一个课程片段的闭环排期，P2 功能不进入当前迭代 |
| 题库质量不足 | 稳定知识点 ID、人工审核、难度校准、错题反馈回流 |
| 个性化“看起来聪明”但无效果 | 使用可解释规则和真实学习指标，不先做黑盒模型 |
| 成本与延迟 | 模型分级、缓存稳定内容、限制上下文、记录 token/耗时/成本 |
| 隐私和越权 | JWT、服务端用户上下文、行级查询约束、删除/导出、审计日志 |
| 文档与代码脱节 | 一个当前路线图、一个状态页；完成标准以测试和可演示行为为准 |
